# Match Pile — Content Report

Generated by the content pipeline in `content/scripts/{generate,validate,build-pack}.ts`,
consuming `src/game/match-pile/{rules,solver,generator}`.

## Generator success rate

`content/scripts/generate.ts` ran `generate({seed, tier})` for seeds `0..199`
(`tier = ['easy','medium','hard'][seed % 3]`, ~66-67 seeds per tier).

**200 / 200 seeds produced a puzzle (100% generator success rate).**

This matches the reverse-construction algorithm's design: every triple draws
3 fresh distinct cells from the entire grid each time rather than depleting a
finite shared "free positions" pool (unlike forward-laid-out Mahjong
boards), so for the grid sizes in `TIER_CONFIG` (≥20 cells, always ≫3) the
construction cannot fail. This is notably better than the ≥95% generator
success-rate bar `solvability.test.ts`#D3 requires.

## Validation funnel

| Stage | Count |
|---|---|
| Generated (seeds 0–199) | 200 |
| Valid (`isValid()` + `solve()` finds a clear + `replay()` confirms it) | 197 |
| Deduped (unique `canonicalKey()`) | 197 |
| Selected into the final pack | 30 |

**3 candidates were rejected**, all for the same reason — `solve()` hit its
50,000-node search budget without finding a full-clear continuation (seeds
29, 56, 110, all originally generated at `tier:'hard'`, i.e. the largest
puzzles: up to 90 tiles / 10 distinct types). This is a **solver search-depth
limitation, not a generator defect**: `generate()`'s reverse-construction
guarantees a valid clear order exists for every puzzle by construction (its
own recorded `.solution` always replays clean — see the R-GEN-SOLVABLE test),
but the independent bounded-DFS `solve()` used for content validation doesn't
share that proof and can occasionally run out of budget on the largest, most
branchy hard-tier boards before its heuristic finds a path. Zero rejections
came from `isValid()` or `replay()` failures.

No duplicates were found (0 candidates dropped by `canonicalKey()`) — with
positions drawn from a 20–25 cell grid per puzzle, two independently-seeded
puzzles landing on an identical `(col,row,layer)` layout is vanishingly
unlikely across only 200 seeds.

## Final pack: tier histogram

`content/scripts/build-pack.ts` groups the 197 deduped survivors by the tier
they were **actually generated with** (`generate({seed, tier})`'s `tier`
argument — preserved end-to-end from `content/seeds/match-pile.json` through
`content/reports/validation.json`), giving three pools of roughly 65-67
candidates each. Within each pool it sorts ascending by `rate()`'s
difficulty score and samples the pool's target count evenly across that
pool's own score range (not just its easiest edge), so a tier's selection
spans that tier's actual difficulty spread instead of clustering at one end.
The 30 shipped levels are written as three BLOCKS in tier order (all easy,
then all medium, then all hard), each block internally ascending by score.

A level's shipped `tier` field is always the exact tier value `generate()`
was called with for that seed — this is required for
`tests/unit/game/solvability.test.ts`#D3 ("shipped levels regenerate from
their seeds": `generate({seed: l.seed, tier: l.tier}).puzzle` must
deep-equal the stored puzzle — since `tier` controls grid size and the type
pool inside `generate()`, relabeling a puzzle into a different tier than it
was generated with makes it impossible to reproduce). See "Tier-bucketing
bug" below — an earlier pass here bucketed by raw score across the whole
pool instead, which broke exactly this invariant.

| Tier | Selected | Target minimum |
|---|---|---|
| easy | 10 | ≥10 |
| medium | 12 | ≥12 |
| hard | 8 | ≥8 |
| **Total** | **30** | **30** |

Blocks are concatenated in easy→medium→hard order, so adjacent-pair
difficulty never inverts by more than one tier step (D1).

## Tier-bucketing bug (found in review, fixed)

An earlier version of `build-pack.ts` sorted **all** deduped survivors
globally by `rate()` score and cut three contiguous bands off that single
sorted list, relabeling each band as easy/medium/hard by its position in the
score distribution — regardless of which tier the candidate was actually
generated with. That produced a real defect: a puzzle generated with
`tier:'easy'` (e.g. seed 27, 24 tiles) could score high enough to land in
the "medium" bucket, so the pack shipped it with `tier:'medium'`. Since
`tier` is one of `generate()`'s inputs (it selects `TIER_CONFIG`'s grid size
and type-pool range), regenerating that level via
`generate({seed:27, tier:'medium'})` produces a structurally different
puzzle than the one actually stored — failing
`tests/unit/game/solvability.test.ts`#D3's seed-regeneration check.

Fixed by bucketing within each candidate's own generation-time tier (see
above) instead of by a global score cut. Re-ran `build-pack.ts` (reusing the
existing `content/seeds/match-pile.json` and
`content/reports/validation.json` — only the selection/bucketing step
needed to change) and confirmed both
`tests/unit/game/rules.test.ts` (14/14) and
`tests/unit/game/solvability.test.ts` (39/39, including D3) pass.

## Generator RNG note

An earlier pipeline run surfaced a real bug in `generator/seed.ts`: seeding
the LCG directly with small sequential integers (`0, 1, 2, ...`) produced a
near-linear, highly-correlated *first* output, so nearly every seed within a
tier rounded to the same tile count (e.g. almost all `easy` seeds produced
exactly 12 tiles). Fixed by scrambling the seed through an integer hash
finalizer (`scrambleSeed`, Chris Wellons' "lowbias32") before using it as the
LCG's initial state — this decorrelates nearby seeds while keeping
`generate()` fully deterministic and dependency-free. The pipeline was
re-run after the fix; the histogram above reflects the corrected output.
